# 手机上手：从开机到手机里跑起来

只讲操作步骤和踩过的坑。原理和取舍在 [README](../README.md) 里。

本机当前的固定地址（换了机器或换了 tailnet 就变，用 `npm run phone:funnel` 打印的为准）：

| | 地址 |
|---|---|
| Metro（手机连这个） | `https://fastenglish.tail489849.ts.net` |
| 后端接口 | `https://fastenglish.tail489849.ts.net:8443` |
| 手机深链 | `exps://fastenglish.tail489849.ts.net` |

---

## 一、每次开机要做的（电脑上）

开**两个**终端，各跑一条，都得一直开着：

```bash
npm run server        # 后端：数据库、片库、串流、字幕、词典
npm run phone:funnel  # Metro + 确认 Funnel 配置，会打印二维码
```

选哪个 `phone`：

| 命令 | 用在什么时候 | 地址 | 带宽 |
|---|---|---|---|
| `npm run phone` | 手机和电脑在同一个 WiFi | 局域网 IP，会变 | 满速，看模式随便用 |
| `npm run phone:funnel` | 人在外面，想要固定地址 | 固定 | 约 1 Mbps，只够听/读/写 |
| `npm run phone:public` | 人在外面，非要看画面 | 每次重启都变 | 14.5 Mbps |

三条都能再加 `-- --fast`（例如 `npm run phone:funnel -- --fast`）：打生产包，Expo Go 每次开少拉三成，跑得也更快，代价是改代码不热更新。自己在改代码的时候别用。

`phone:funnel` 打印 `[phone] Funnel 早就配好了，直接用。` 是正常的——Funnel 的配置存在 tailscaled 里而不是某个进程里，重启电脑也还在，这条命令只是核对一遍。

### 电脑不能睡

一睡这两个服务就没了，手机侧表现为「地址明明没变却打不开」。这是最常见的一种「坏了」。长时间在外面用的话，先去电源设置里把睡眠关掉。

## 二、手机第一次连（只需一次）

**新版 Expo Go 首页没有「Enter URL manually」了**，也没有内置扫码器，首页只剩「Development servers」的说明文字和「Recently opened」列表。所以别在 App 里找输入框，走下面两条之一。

### 办法一：用系统相机扫码

`npm run phone:funnel` 启动时会在终端画一个二维码，**用 iPhone 自带的相机 App 对着它扫**，iOS 会弹提示问要不要用 Expo Go 打开。

想单独出一张码（可以顺便存成图片发给别人）：

```bash
node scripts/qr.mjs https://fastenglish.tail489849.ts.net
node scripts/qr.mjs https://fastenglish.tail489849.ts.net code.png
```

### 办法二：把深链发到手机上点开

把这行发到手机（微信文件传输助手、备忘录、AirDrop 都行）：

```
exps://fastenglish.tail489849.ts.net
```

有些聊天软件不会把 `exps://` 识别成可点的链接，那就复制这行文本，粘到 **Safari 地址栏**回车，一样会唤起 Expo Go。

连上一次之后它就躺在「Recently opened」里了，以后点一下就行，不用再扫。列表里那些连不上的旧条目（以前的局域网 IP、Cloudflare 隧道地址）用右上角 CLEAR 清掉。

### scheme 必须是 exps，不是 exp

这一条单独拎出来，因为报错完全看不出原因。

Expo Go 把 `exp://` 一律换成 `http://`，只有 **`exps://`** 才换成 `https://`。隧道后面只有 https，用 `exp://` 就是拿明文去敲 TLS 端口，Expo Go 里报：

> There was a problem running the requested app.
> Unknown error: The network connection was lost.

**也别加 `:443`。** https 默认就是它；更要紧的是万一碰上不认 `exps` 的 Expo Go 版本退回了 http，不带端口是 `http://主机` → 80 端口 → Tailscale 那里有个 302 跳到 https，还能救回来，而写死 `:443` 就是明文打 TLS，必死。

还有一点反直觉的：**Expo CLI 自己在终端画的那个二维码，在 https 隧道场景下是错的**。它的 `UrlCreator` 检测到 https 代理时只把端口补成 443，scheme 仍然留着 `exp`，拼出来正好是上面那个连不上的形式。所以 `scripts/qr.mjs` 自己画了一个，别去扫 Expo 打的那个。

## 三、连上之后

### 每次打开都要重下一遍包，这是 Expo Go 的机制

**不是只有第一次慢。** Metro 发包时带的是 `Cache-Control: no-store, no-cache, must-revalidate`，Expo Go 存不下来，退出再进就得整个重拉。别指望「第二次会快」。

第二次确实会快一点，但快在**服务端**：Metro 的转译结果有缓存，首次冷启动打包要二三十秒，之后几秒就出包。省掉的是打包时间，不是下载时间。

还有一点：Metro 的响应**没有 `Content-Length`**（分块传输），也不支持 Range。所以进度条根本没法显示，中途息屏断掉也只能从 0 重来，这两条都不是能改的。

这个项目的包实测（iOS，Hermes 字节码，过网的是 gzip 那一列）：

| | 原始 | gzip 后 |
|---|---|---|
| 开发档（默认） | 3.98 MB | 1.21 MB |
| 生产档（`--fast`） | 1.72 MB | 0.51 MB |

Funnel 约 1 Mbps，开发档十几秒，生产档八九秒。

三条路，按效果排：

1. **回局域网**。`npm run phone`，同一个 WiFi 下一秒之内。差距是数量级的，能用局域网就别用 Funnel。
2. **加 `--fast`**。`npm run phone:funnel:fast` 打生产包，过网体积少 58%，而且跑起来也更快（没有开发模式那些检查）。代价是改代码不会热更新——只用不改的时候开它。
3. **做开发构建**。JS 直接编进 App，打开就是零下载，还顺带解决锁屏听（见第六节）。要 Mac 跑 `npx expo run:ios`，或者用 EAS Build。这是唯一能彻底摆脱「每次重下」的办法。

`npm run phone:public` 也能救急（14.5 Mbps），代价是地址每次变、得重新扫码。

### 在外面别切看模式

外网环境下 App 会自动落在**听模式**，这是对的，只传音轨，一小时 29 MB。看模式要 5 Mbps，Funnel 给不到（约 1 Mbps），画面会一直卡。读模式和写模式压根不碰媒体流，随便用。

真想在外面看画面：手机上也装个 Tailscale 登同一个账号，**地址一个字都不用改**，但流量会改走设备间直连，绕开 Funnel 的限速，瓶颈变回你家的上行带宽。

模式的选择是分环境记的：在家关掉听模式，出门不会跟着变，两边各记各的。

## 四、出问题时按这个顺序查

| 现象 | 多半是什么 | 怎么办 |
|---|---|---|
| `The network connection was lost` | 用了 `exp://` 而不是 `exps://` | 换 scheme，见上面 |
| Expo Go 一直转圈 | 在拉包（开发档 1.2 MB） | 外网等满一分钟再判断。每次打开都要重拉，不是只有第一次，见上面 |
| 扫码后没反应 | 电脑睡了，或两个终端有一个没开 | 看两个终端还在不在 |
| 能进 App，一登录就转圈 | 后端没起来 | 另开终端 `npm run server` |
| `unexpected state: NoState` | Tailscale 托盘程序没起来 | `phone:funnel` 现在会自己拉起来；手动的话开 `C:\Program Files\Tailscale\tailscale-ipn.exe` |
| 画面卡成幻灯片 | 在外网切了看模式 | 切回听模式，或手机装 Tailscale |
| 全片单词报「词典查询超过 60 秒」 | 外网太慢，响应传不完 | 换个网络重进片子。这个响应已经压到 86 KB，正常 5 秒左右；还超时说明链路确实很差 |
| 地址变了 | 用的是 `phone:public` 不是 `phone:funnel` | 换命令 |
| 听模式/读模式放不出原声，合成音正常 | 音轨这条流没连上 | 照下面那节查 |
| 换了新片子，听模式点了没声 | 这部片的音轨还没切片 | 等一会儿，界面会显示准备进度；老片子只要切片，几秒就好 |
| 中途切过 WiFi/5G，之后一直放不出原声 | 播放器僵在 loading，把音轨判死了 | 状态行显示 `loading · 已暂停 · 缓冲0s`，且这个数一直不涨。25 秒后自动换地址重挂，最多 3 次；用完了点状态行右边的「重连」。**缓冲数在涨就是正常缓冲，别点重连** |
| 放过一阵子，隔一会儿再点就没声，日志里分片全是 200 | 音频会话被朗读或息屏拿走了 | 已经在朗读结束、回前台、播放前都补调了重设；还遇到就记下当时点过什么 |
| 双击远处的台词，要等半分多钟才出声 | 预读太多，加上看门狗把缓冲中的播放器反复推倒重来 | 见下面「跳到远处的台词要等很久」和「卡住重连的看门狗会误杀跳转」 |

### 原声放不出来时看哪里

合成音是手机本地念的，不走网络；原声要从后端拉音轨。所以「合成音能放、原声不能放」基本就是音轨这条流的问题，跟播放按钮、跟静音键都无关。

先问一句**中途有没有切过网络**——切过就大概率是下面「切网络之后就再也放不出原声」那一节，跟当前网速无关。

判断得靠后端终端的串流日志，界面上看不出来。正常起播长这样——先要播放列表，然后一个接一个地取分片：

```
[fastenglish] 200 GET /api/movies/1/audio.m3u8 sent=2KB 12ms
[fastenglish] 200 GET /api/movies/1/audio/seg/seg00000.ts sent=86KB 1310ms 66KB/s
[fastenglish] 200 GET /api/movies/1/audio/seg/seg00001.ts sent=87KB 1280ms 68KB/s
```

- **一条 `audio.m3u8` 都没有**：手机压根没发起请求，检查登录和网络。
- **`audio.m3u8` 返回 409**：这部片子还没切片，等准备完成。
- **`401`**：令牌过期，在 App 里重登一次。
- **只有播放列表、没有分片**：列表拿到了但解不了，多半是分片地址拼错，看列表里那几行是不是 `audio/seg/xxx.ts?token=...`。
- **分片一直 `断开`**：链路太差，看 `KB/s`。音轨播放本身只要 8 KB/s，长期低于这个数就跟不上。

`sent` 的读法有个坑，见下面「读日志时别把 sent 当成手机收到的量」。

### 听模式放的是 HLS，不是整段 MP4

这是外网能不能用的关键，改过来之前折腾了很久。

整段 MP4 的文件头里有一张逐帧索引表，**播放器必须连续把它整个拿到才出得了声**。表的长度只跟「采样率 × 时长」有关，两小时的片子在 48kHz 下约 1.4 MB。外网只有几十 KB/s，要等二十多秒，中途抖一下就前功尽弃，撞上 AVPlayer 那个 60 秒超时。

切成 HLS 之后，起播只要「播放列表 + 一个分片」：

| | 整段 MP4 | HLS |
|---|---|---|
| 起播要下载 | 1.4 MB 索引表 | 2.4 KB 列表 + 86 KB 首片 |
| 66 KB/s 下起播 | 22 秒 | 1.3 秒 |
| 断一次网 | 全部作废，从头再来 | 只重取那一个分片 |

分片 10 秒一个，两小时切出 790 个，切片只是重新封装不重编码，`-c copy` 六秒就跑完。播放列表 790 行里每行都缀着同一个令牌，压缩后从 70 KB 降到 2.4 KB。

几个实现上不显然的点：

- **分片用 TS 不用 fMP4**。`ffmpeg-static` 这个构建下 `-hls_segment_type fmp4` 只写分片、不写 `init.mp4`，缺了初始化分片整条流都解不了。TS 自带解码信息，不需要它。
- **令牌要逐行缀到每个分片地址上**。播放器取分片时不会把播放列表地址上的查询串带过去，只在列表那一条上带令牌是不够的。
- **分片地址要写成 `audio/seg/<name>`**。播放器按播放列表的地址解相对路径，基准是 `/api/movies/<id>/`，用 ffmpeg 写的裸文件名会解到不存在的地方去。
- **整段 `/audio` 接口留着当退路**，也给浏览器直接下载用。

老片子早就抽好整段音轨了，只差切片：`build()` 认这种情况，跳过抽音直接切，不会白花几分钟重抽。

三个已经踩过的坑，别再走回去：

- **不要在加载途中按时间退避重连**。加过 1/3/8 秒退避的版本，反而把能放的搞成放不了：换源等于让播放器从零重连，之前下到一半的文件头全作废。日志里第一次尝试已经读到 704 KB、速度 256 KB/s，索引表总共 724 KB，就差最后一点被掐断，之后每次都从头开始。慢链路上「多等一会儿」几乎总比「重来一次」划算。只在播放器**明确报 error** 之后才换源重挂，见下一节。
- **听模式下不要再去加载原片**。以前音轨没备好时会先放着原片，结果手机同时拉 4.8 GB 的片子和音轨，平分带宽，音轨永远拿不完那张索引表。现在音轨没好就什么都不放（`App.tsx` 的 `playerSource` 里 `if (!listening) return null`）。日志里出现 `/stream` 和 `/audio` 交替的「断开」就是这个坑又回来了。
- **播放按钮不是原因**，别再往这条路上查。曾经因为「加了按钮就放不出原声」把整行控制条来回删了几遍，后来在完全没有按钮的版本上照样超时，证明是巧合。

### 跳到远处的台词要等很久

双击一句离当前位置很远的台词，界面会停在 `loading · 已暂停` 半分钟到一分钟。声音最后是能出来的，但慢得没法用。

原因在播放器那边，不在网络：AVPlayer 的 `preferredForwardBufferDuration` 默认是 0，意思是「你自己看着办」，它在两小时的资源上选得极其激进——日志里一次跳转能引发连续五十多个分片请求，约 5 MB。1 Mbps 下正好是一分钟。而听一句话只需要几秒的音频。

叠加的第二件事是 `waitsToMinimizeStalling` 默认为 `true`：即使数据够了，它还要等到自认为「能一口气播完不卡」才出声，慢链路上这个估算同样保守得离谱。

所以听模式下两个都改掉（`App.tsx` 里跟着 `listening` 走）：

```ts
player.bufferOptions = listening
  ? { preferredForwardBufferDuration: 30, waitsToMinimizeStalling: false }
  : {};
```

30 秒就是 3 个分片。音轨只有 64 kbps、8 KB/s，30 秒的存量足够扛抖动。看模式保持默认，画面要的余量比这大得多。

**`bufferOptions` 必须整个对象赋值**，改单个字段不生效，这是 expo-video 明说的。

只改缓冲还不够，真正的大头是下面这条。

### 卡住重连的看门狗会误杀跳转

压完缓冲之后跳转还是要等三四十秒，日志暴露了原因——那半分钟是 App 自己造成的，不是网络：

```
audio.m3u8            ← 取了 6 次（VOD 播放列表正常只取一次）
seg00000.ts           ← 取了 3 次（每次重建都先从头加载再 seek）
seg00007.ts           ← 重复 6 次
```

这是播放器被反复推倒重来的样子。凶手是「loading 超过 15 秒就换地址重挂」那个看门狗：它纯按时间判死，分不清「asset 死了」和「正在为跳转缓冲」。15 秒 × 3 次重试正好三四十秒，**重试次数用完、看门狗不再开火之后，播放器才终于安静地缓冲出声**——用户体感的「等半分钟就好了」正是它退场的那一刻。

这和上面记过的教训是同一个：慢链路上「多等一会儿」几乎总比「重来一次」划算。当时删掉了退避重连，后来为了救「切网络后僵在 loading」又以 15 秒的形式加了回来。

判据要换成**有没有数据进来**，而不是等了多久：

```ts
const buffered = player.bufferedPosition;   // 缓冲时往前爬，asset 判死时一动不动
if (buffered !== seen) { seen = buffered; flatSince = Date.now(); return; }
if (Date.now() - flatSince >= STUCK_MS) reloadAudio();
```

`bufferedPosition` 返回的是「包含当前播放位置的那段已加载区间的末尾」，取不到就返回 0（见 expo-video 的 `getBufferedPosition`）。跳转时它会从 0 跳到目标位置往后，随分片到达持续增长；asset 被判死时则始终是 0。阈值放到 25 秒，因为有了缓冲上限，最慢也就是等 3 个分片、260 KB。

诊断行在 `loading` 时会显示 `缓冲Ns`，就是这个数——**在涨就别点重连**。

另外分片响应加了 `Cache-Control: private, max-age=604800, immutable`。分片内容永不变化（片子 id 加序号就唯一确定它），不设的话反复重下——日志里同一个分片出现过六次，因为每次跳回同一句都要重新拉。`private` 是因为地址上带着令牌，不能进共享缓存。播放列表相反，逐行缀着令牌，标了 `no-store`。

### 切网络之后就再也放不出原声

这是伴生的第二个问题，HLS 治不了它，得单独修。

现象：中途切过网络（WiFi↔5G）之后就一直放不出来，**切回原来那个网络也不行**，必须把 Expo Go 从后台划掉重开。原因是切网时在飞的连接会断，iOS 的 AVPlayer 把这个 asset 判死并记住，之后同一个地址怎么点都是原来那个结果。而 `audioUrl` 以前生成的地址一个字都不变，`playerSource` 的 memo 结果就不变，播放器压根不会重新 `replace`。

修法是让重试用一个不同的地址逼出新 asset：`audioUrl(movieId, attempt)` 在 attempt > 0 时缀上 `&r=<attempt>`（服务端只认 `token`，多的参数忽略）。

**触发条件不能只认 `status === 'error'`**，这是踩过的坑。实测坏掉时 AVPlayer 是**僵在 `loading` 上、从不报错**的：分片一路 200 拿着，界面显示「loading · 已暂停」，那个 error 永远等不到，所以按 error 写的自动重挂一次都没跑过。现在两条都认：

- `statusChange` 收到 `error`，立刻重挂。
- `loading` 持续超过 15 秒，重挂。正常起播只要一两秒，这个阈值不会误杀慢链路。

同一部片子最多自动重来 3 次，用完了还有听模式状态行右边的「重连」给人手动点。

走 HLS 之后这套才划算：重来的代价只是一个 86 KB 的分片，不像整段 MP4 那样得重啃 1.4 MB 的索引表。

### 听模式那行灰色状态是干什么的

播放条下面那行小字（`src/hooks/usePlayerProbe.ts`）显示播放器**自己报的**状态。加它是因为原声排查了很多轮都在猜：服务端日志只能证明「分片发出去了」，证明不了手机那头在干什么，而下面这几种情况在服务端看来一模一样：

| 显示 | 含义 | 往哪查 |
|---|---|---|
| `readyToPlay · 播放中`，但没声 | 在放，声音被系统吞了 | 音频会话／输出路由 |
| `readyToPlay · 播放中 · 进度没动` | 在放但时间轴卡住 | 缓冲 |
| `loading · 已暂停` | **压根没就绪**，最常见 | 上一节，等自动重挂或手点重连 |
| `error` + 红字 | 播放器明确报错 | 红字直接定性 |
| 带`静音`或`音量0.x` | 音量被谁改了 | 找改它的代码 |

**这一行只读，不做任何补救**，别在这儿加自动重连逻辑，理由见上面踩过的坑。

### 分片一路 200，手机就是不响

**这个不是网络问题，是音频会话被别人拿走了。** 判断方法很干脆：看后端日志，如果分片在源源不断地 200，数据就是到了手机上，喇叭不响只能是播放器这一侧的事。

iOS 的音频会话是全系统共享的，开机配一次远远不够：

- **朗读**用的 `AVSpeechSynthesizer` 念完会把会话释放掉。我们配的是 `doNotMix`（非混音），一释放播放器就变成「在播但没声」——进度在走、分片在拉、一点动静都没有。
- **息屏、来电、切去别的 App** 同理。

所以在三个地方补调了 `reclaimAudioSession()`（`src/lib/audioSession.ts`）：朗读结束、App 回到前台（`AppState` 变 `active`）、以及 `playVideo()` 真正出声之前。这个调用很轻，重复调没有副作用，宁可多调也别漏。

典型的复现路径：进去能放 → 中间点过跟读或单词发音 → 隔一会儿再双击台词就没声了，而日志里分片全是 200。

### HLS 分片是 .ts 后缀，跟 TypeScript 撞名

`data/` 得从前端工具链里排掉，两处都要：

- `tsconfig.json` 的 `exclude`，否则 `tsc --noEmit` 会把几百个音频分片当源码编译，刷一屏「File appears to be binary」。
- `metro.config.js` 的 `resolver.blockList`，否则 Metro 会当源码去解析，而且一部片子近八百个分片白白压在文件监听上。

### 读日志时别把 `sent` 当成手机收到的量

排查中途在这上面栽过一次。日志里的 `sent` 是服务端往 socket 写进去的字节数，走 Funnel 时对端是本机的 tailscaled，它会大口吃下再慢慢转发，所以 `sent` 会明显高于手机实际收到的量。

当时看到「成功那次 66 KB/s、失败那次 45 KB/s，一个量级」，就断定跟带宽无关，方向偏了一阵。**大额传输的数字是可信的**（缓冲吃不下几 MB），小额的不可信。要判断手机端真实速度，看它连续拿到数据的那条长记录，别看几秒就断开的那些。

### 还嫌慢的话可以动的旋钮

按优先级：

1. **手机装 Tailscale**，见下一节。绕开 Funnel 的限速，比什么都管用。
2. **分片切短一点**。`server/audio.js` 的 `SEGMENT_SECONDS`，默认 10 秒；改成 5 秒起播再快一倍，代价是分片数翻倍、播放列表变长。也可以用环境变量 `FASTENGLISH_AUDIO_SEGMENT`。
3. **降采样率**。在抽音的 ffmpeg 参数里加 `-ar 24000`，音轨体积减半。改完要重抽（`audio.build`），两小时的片子几分钟。这条现在优先级低了——HLS 之后起播不再取决于整个文件的大小。

### 手机上装 Tailscale，比什么优化都管用

Funnel 是公网入口，流量走 Tailscale 的中继，带宽被限得很死，日志里手机实测只有 **24～108 KB/s**。音轨播放本身只要 8 KB/s，够用；难的是起播那一下，所以才有了上面的 HLS。看模式要 5 Mbps，怎么优化都跑不动。

手机装上 Tailscale 客户端登进同一个 tailnet 之后，`fastenglish.tail489849.ts.net` 这个域名不变，但流量改走 WireGuard 直连，不再经中继，快一个数量级。看模式也是这时候才跑得动。外网用得多就装一个。

服务是不是真的活着，一条命令看全：

```bash
node --input-type=module -e "for (const [n,u] of [['后端','http://localhost:4000/api/health'],['Metro','http://localhost:8081/status']]) { try { const r=await fetch(u); console.log(n, r.status); } catch { console.log(n, '不通'); } }"
```

从公网这一侧验（本机 MagicDNS 会把域名解析到内网地址，直接 curl 测不出真实情况，得把连接钉到 Tailscale 的公网入口）：

```bash
node --input-type=module -e "
import { execFileSync } from 'node:child_process';
const h='fastenglish.tail489849.ts.net';
const d=await fetch('https://dns.google/resolve?name='+h+'&type=A').then(r=>r.json());
const ip=d.Answer.find(a=>a.type===1).data;
console.log(execFileSync('curl.exe',['--resolve',h+':8443:'+ip,'-sS','https://'+h+':8443/api/health'],{encoding:'utf8'}));
"
```

## 五、收摊

不想让这台机器继续挂在公网上：

```bash
tailscale funnel reset
```

两个地址立刻失效，本地和局域网不受影响。想再挂回去，下次跑 `npm run phone:funnel` 会自动重新配好。

## 六、Expo Go 里试不出来的两件事

- **锁屏听**。后台播放要靠 `app.json` 里 expo-video 插件往 Info.plist 写 `UIBackgroundModes=audio`，而 config plugin 只在真正出包时才生效，Expo Go 用的是它自己那份 Info.plist。想要这个功能得走开发构建（`npx expo run:ios` 需要 Mac，或者用 EAS Build）。
- **.mkv 的看模式**。iOS 的播放器不认这个封装，点开只有黑屏。听模式不受影响（服务端用 ffmpeg 抽成 m4a 再发），读模式和写模式也不碰视频。想在手机上看画面就先把片子转成 mp4。
